# V6.1 重构计划：随机播放 / 切模式卡顿 / 1:50 卡住 / 设置持久化

本文件是 V6.1 的施工单与验收记录，对应用户报的三件事：

1. 切换随机/循环模式时有卡顿；
2. 有些歌播到 1 分 50 秒会「卡住」；
3. 按键选择后应该保存，下次打开 app 一样生效（点名均衡器）。

术语以 [GLOSSARY.md](../GLOSSARY.md) 为准；决策理由见
[docs/adr/0001](adr/0001-shuffle-cycle-and-play-history.md) 与
[docs/adr/0002](adr/0002-detect-silent-stalls.md)。

## 1. 随机播放：一条 Shuffle cycle 播完才重洗

**现状问题**：`PlayerController.onMediaItemTransition` 每次换歌都
`shuffleState.invalidate()`，把整条 permutation 丢掉；`next()` / `prev()` 又用
`redrawNext` / `redrawPrevious` 各抽一条新序。两条路径各自抽样，等价于「在其余
n-1 首里均匀随机」，20 首队列前 10 首出现重复的概率约 89%。

**做法**：

| 改动 | 文件 |
| --- | --- |
| 换歌不再 `invalidate()`，cycle 跨曲存活 | `player/PlayerController.kt` (`onMediaItemTransition`) |
| 按钮走 `nextIndex` 而不是 `redrawNext` | `player/PlayerController.kt` (`next()`) |
| 自动续播走同一条 cycle | `player/PlayerController.kt` (`advanceAfterTrackEnd()`) |
| cycle 末位以当前曲为锚重画新 cycle | `player/RandomShuffle.kt` (`cycleFrom`) |
| 周期起点问 prev 返回 -1（= 重播当前曲） | `player/RandomShuffle.kt` (`previousIndex`) |

**验收**：`RandomShuffleStateTest`（17 项）、`RandomShuffleOrderTest`（11 项）、
`RandomShuffleCloneTest`（7 项）、`ShuffleStallProbe`（8 项）全绿；
`oneCycleCoversEveryTrackExactlyOnce`、`theCycleSurvivesATrackChange`
（断言 `cycles == 1`）为契约。

## 2. 上一首 = 播放历史回退

**现状问题**：`prev()` 的 KDoc 写着回退历史栈，实现是再抽一次随机。随机模式下
「cycle 的前一位」是一首本轮还没播过的歌，听起来像往前跳。

**做法**：新增 `player/PlayHistory.kt`（bounded 200 条）。
`confirmBack()` 弹栈并记下 `expected`，`onTrackChanged()` 只有在 `expected`
匹配时才不压栈——用「弹栈后记 expected」代替「历史 + 回退中布尔标记」，因为后者
要在每条换歌路径复位，漏一处就把栈吃掉。历史为空时重播当前曲。

**验收**：`ShuffleStallProbe.appPrevGoesBackToTheTrackActuallyHeard`、
`appPrevAtTheStartRestartsWithoutStalling`。

## 3. 切换模式卡顿

**根因**：`installShuffleOrder()` 每次都用 `ExoPlayerImpl.setShuffleOrder` 装一份
新 order；该方法内部 `createMaskingTimeline()` 造一个新的 `PlaylistTimeline`
实例，而 `PlaylistTimeline` 没有重写 `equals`，于是 `updatePlaybackInfo` 里
`Timeline.equals` 必然为 false → 派发 `onTimelineChanged` → app 的
`onTimelineChanged` 又调 `installShuffleOrder()` —— 一次开关随机变成一串
rebuild，跨进程的 `MediaController` 再把每一轮放大成主线程停顿。

**做法**：`installShuffleOrder()` 记住已装 order 的
`RandomShuffleState.version`（generation）与 playlist 长度，两者都没变就直接
return。整表重建（`setMediaItems` / `clearMediaItems`）之前调
`forgetInstalledOrder()` 把记忆清掉。

**验收**：连续 `toggleShuffle()` 不再触发额外的 `onTimelineChanged` 链；模拟器
上切换模式无明显停顿。

## 4. 播放到 1:50 卡住

**现象**：位置停住但 `isPlaying` 仍为 true，不抛 `onPlayerError`，所以 app 里
没有任何路径会响应。

**做法**：新增 `player/StallWatchdog.kt`（不依赖任何 Android 类型，纯函数式
`onTick(position, playing, buffering, now)` → `NONE / RETRY / REBUFFER`），接在
既有的 300ms 进度循环上：

- 播放中位置 8s 不动 → `RETRY`：`prepare()` + `seekTo(位置)` + `play()`；
- 同一处再冻 8s → `REBUFFER`：重新解析 URL（在线曲目多半是流地址过期）或重开
  文件，从冻结点续播；
- 位置一动就把计数清零，所以每次冻住都有自己的廉价重试；
- 缓冲中（`STATE_BUFFERING` 且 `isPlaying == false`）单独计时 20s，因为
  `isPlaying` 分支永远看不到这种冻住。

**验收**：`StallWatchdogTest`（7 项，假时钟精确断言预算）。

## 5. 设置持久化（均衡器）

**现状问题**：`EqualizerController.attach()` 每次新 audio session 都
release + 重建效果器，并把所有 band 电平清零——所以调好的曲线每次启动都白调。

**做法**：

| 层 | 改动 |
| --- | --- |
| 数据 | 新增 `data/settings/EqProfile.kt`（enabled / preset / bands / bass / virtualizer / loudnessMb）——落在 `data.settings` 而不是 `player`，因为依赖方向是 player → data |
| 持久化 | `SettingsStore` 加 6 个 `KEY_EQ_*` + `setEq()` + `AppSettings.eq` + `toSettings()` 映射 |
| 效果器 | `EqualizerController` 加 `setProfile()` / `snapshot()` / `applyProfile()`；`attach()` 成功后自动灌回 |
| 接线 | `MainViewModel` 在 `settingsStore.loaded` 后 `equalizer.setProfile(st.eq)`；7 个 `eqXxx()` 改完即 `persistEq()` |

`applyProfile()` 必须**最后**才设 `enabled`：`setBassStrength` 等内部有
`if (strength > 0 && state.enabled)` 的守卫，先开会被吃掉。

**验收**：`SettingsTest` 覆盖新键的默认值与读取；模拟器上改曲线 → 杀进程 →
重开，曲线仍在。
